# Personal OS 6.4 — MVP foundation

## Что меняется

- Большая адаптивная шкала выполнения плана без сломанной подписи; её ширина ограничена 100%, цвет отражает 100–200%.
- Настройки больше не показывают устаревшие недельные KPI «задачи, продажи, тренировки». Значения в базе сохраняются для совместимости старых Edge Functions.
- На Главной обычные и амбициозные цели без старых недельных целей.
- Буфер: поиск, чипы категорий, визуальная группировка, дополнительные страницы свёрнуты.
- Открытая задача: полноширинный редактор, «Назад в буфер»; Split Pipeline — явная ошибка при пустом поле и Enter/галочка для добавления.
- Текстовые блоки: автосохранение после паузы и при уходе из поля, индикация ошибки и повтор.
- Рабочая задача: запланированный/подтверждённый доход (RUB/USD/EUR, дата фактического получения).
- Аналитика: обычные/амбициозные цели, связанные задачи, буфер, 7/28/90 дней задач, дисциплина, вызовы, подтверждённый доход по валютам.
- Защита блоков задачи при удалении: архивирование страницы и восстановление при обратной вставке задачи с прежним ID.

## Безопасная установка в GitHub + Supabase

0. Сначала **сделай резервную копию Supabase** (таблицы `personal_tasks`, `os7_pages`, `os7_blocks`, `os7_splits`, `os7_workflow_items`, `os8_regular_goals`, `os8_task_pages` и всю схему, если есть доступ). Скачай ZIP текущего GitHub-репозитория. Рекомендуется отдельная ветка и проверка PR.
1. Убедись, что установлены изменения 6.3, в том числе таблицы `os8_task_pages` и `os8_regular_goals` и `os7_pages`.
2. Supabase → SQL Editor → New Query: **один раз выполни** `supabase/07-os9-mvp.sql`. Миграция добавляет только новые таблицы, меняет два триггера для защиты удалённых страниц и ничего не очищает.
3. Supabase → Edge Functions → Deploy new function → Via Editor: имя `os9`, файл `supabase/08-os9-index.ts` скопировать как `index.ts`. `Verify JWT = OFF` **только для `os9`**, поскольку функция сама проверяет подпись Telegram initData. Понадобится `TG_BOT_TOKEN` и стандартный сервисный ключ Supabase внутри Edge Functions Secrets. Секреты **не** записывать в GitHub.
4. Проверь, что все существующие функции `dashboard`, `os6`, `os61`, `os7`, `os8`, `telegram-webhook` продолжают работать; их код менять не нужно.
5. Через github.dev скопируй в репозиторий содержимое релиза 6.4 (папки `src`, `tests`, `supabase`, а также `package.json`, `.github/workflows/deploy.yml`, `INSTALL_6_4.md`). Не загружай `node_modules`. Старый `index.html` не надо удалять: точка входа та же.
6. Commit + Push в рабочую ветку; GitHub Actions запускает smoke, workspace, unified и MVP regression tests, затем `tsc --noEmit && vite build`. **До зелёной сборки и приёмки не сливай PR в main.**
7. Проверка в Telegram и на MacBook: (а) открыть старую задачу и вернуться, (б) создать Split с пустым названием — увидеть ошибку, (в) добавить Split по Enter, (г) изменить блок и проверить сохранение после перезапуска Mini App, (д) изменить цель и увидеть обновление Главной, (е) связать задачу с обычной целью, (ж) подтвердить доход и проверить аналитику, (з) удалить задачу со Split Pipeline и восстановить её с прежним ID — убедиться, что блоки сохранены.

## Важные ограничения

- Рабочий код 6.4 здесь **не был проверен полной production-сборкой**: доступ к npm registry недоступен (`EAI_AGAIN`). Статические и Node-тесты прошли; typecheck и визуальный тест должны пройти в GitHub Actions и на реальных устройствах.
- Удалённые задачи сохраняют свои страницы в архиве без автоматического срока очистки: это защита от потери данных. Финансовые поступления по задачам не удаляются каскадно: это отдельная запись фактически заработанных денег. Полноценная корзина и retention-политика — отдельная задача.
- Восстановление старой страницы автоматически работает при повторной вставке задачи с *тем же ID*; надо проверить реальную реализацию `task_restore` действующей Edge Function.
- Доход — по дате **подтверждённого получения**, не по запланированной дате задачи. Валюты не конвертируются.
- Текущий процент обычных целей остаётся ручным. Связанные задачи показывают количество выполненных, но не меняют процент без согласованной формулы.
- График задач привязан к данным существующего `os6.metrics`. Если тот сервис агрегирует по дате плана, график показывает задачи в разрезе плановых дат, а не фактический timestamp завершения; для точной аналитики нужна отдельная дата выполнения.
- Аудит security/performance требует проверки в реальном Supabase, а UX — мобильного тестирования. Ничего в рабочем GitHub или Supabase автоматически не изменялось.

## Откат

- Если frontend не проходит сборку — не публиковать, исправить errors в Actions.
- Если проблемы после публикации — верни предыдущий frontend commit через GitHub; **не откатывай** миграцию удалением таблиц, пока не сохранены новые доходы и связи.
- Восстановить старую схему триггеров только после отдельной проверки, иначе возможно удаление блоков страниц.
